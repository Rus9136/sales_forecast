## 2. Стратегия реализации

### 2.1 Принцип: четыре параллельных трека

Вместо линейных этапов ТЗ (Discovery → Data → ML → LLM → Dashboard → Pilot) применяется подход параллельных треков с ранней доставкой ценности:

| Трек | Суть | Приоритет |
|---|---|---|
| **A. Данные и витрины** | Backfill чеков, аналитические витрины, качество данных | Критический (блокирует всё) |
| **B. Ценовой движок** | Кластеризация → эластичность → оптимизатор → правила | Критический (ядро системы) |
| **C. UX + LLM** | Дашборд KPI, UI рекомендаций, LLM-обоснования, отчёты | Высокий (то, что видят пользователи) |
| **D. Конкурентный анализ** | Парсер, мэппинг позиций, Price Index | Средний (не блокирует MVP) |

## 3. Трек A: Данные и витрины (недели 1-6)

### A1. Backfill чеков за 24 месяца (недели 1-3) — ⏳ В ПРОЦЕССЕ (~95%)

**Цель:** загрузить полную историю транзакций за 2024-06 .. 2026-05 в `receipt` / `receipt_item`.

**Текущий статус (2026-05-26):**
- **2,260,652 чеков** / **9,254,187 позиций** за период **2024-06-01 .. 2026-05-25**
- **2,057,953 строк** в `sku_daily_sales` (агрегированы автоматически)
- ✅ Definition of done выполнен: ≥ 2 млн чеков, ≥ 18 месяцев

**Подход:**
- Использовать существующий `iiko_receipts_loader.py` с параметрами `from_date` / `to_date`.
- Загружать чанками по 2 недели (iiko OLAP может timeout'иться на больших периодах).
- После каждого чанка — агрегация в `sku_daily_sales` через `sku_daily_aggregation_service.py`.
- Запускать ночью, чтобы не нагружать iiko в рабочее время.

**Риски:**
- iiko OLAP timeout на старых данных → уменьшить чанк до 1 недели.
- Себестоимость (`ProductCostBase`) может быть недоступна за старые периоды → заполнить средней маржой категории.
- Старые `DishId` не найдутся в `product` (удалённые позиции) → `product_id = NULL`, snapshot-поля сохраняются.

### A2. Аналитические витрины (недели 3-4) — ✅ ВЫПОЛНЕНО (2026-05-26)

**Цель:** создать предагрегированные таблицы для моделей и дашборда.

**Реализованные таблицы:**

1. **`sku_price_history`** (78,934 строк) — фиксация каждого изменения фактической цены позиции:
   - `product_id`, `department_id`, `price`, `prev_price`, `change_pct`, `first_seen_date`, `last_seen_date`
   - Заполняется из `sku_daily_sales` (derived avg_price = total_sum/total_qty): когда цена дня ≠ цена предыдущего дня → новая строка.
   - Детекция изменений через SQL-window `LAG()` + контекст `from_date - 1` для инкрементальных запусков.
   - Критично для модели эластичности: каждая строка — одно «ценовое событие».

2. **`sku_weekly_summary`** (595,266 строк) — агрегат по SKU × подразделение × ISO-неделя:
   - `total_qty`, `total_revenue`, `total_cost`, `gross_profit`, `gp_margin`
   - `avg_price`, `avg_daily_qty`, `unique_receipts`, `days_with_sales`
   - `qty_cv` (coefficient of variation = std/mean — стабильность спроса)
   - `cost_coverage` — доля позиций с ненулевой себестоимостью (для предупреждений в UI)

3. **`department_weekly_summary`** (2,970 строк) — агрегат по подразделению × ISO-неделя:
   - `total_revenue`, `total_cost`, `gross_profit`, `gp_margin`
   - `total_receipts`, `avg_receipt_sum` (AOV), `unique_guests`
   - `cost_coverage`

**Реализация:**
- Миграция: `migrations/019_pricing_analytics_views.sql`
- Модели: `app/models/pricing_analytics.py` (3 SQLAlchemy-модели)
- Сервис агрегации: `app/services/pricing_analytics_service.py` (SQL INSERT...SELECT ON CONFLICT, чанкованный upsert)
- Scheduler: `app/services/scheduled_pricing_analytics.py` → ежедневно 04:30 (price history 3 дня + weekly summaries текущая+предыдущая неделя)
- API: `app/routers/pricing_analytics.py` — 5 endpoints (GET price-history, sku-weekly, department-weekly + POST aggregate, backfill)

**Верификация:**
- Cross-check revenue: weekly = daily (точное совпадение на полных неделях)
- week_start всегда понедельник (DOW=1, ISO 8601)
- Себестоимость: COALESCE(cost_price, 0) с отслеживанием cost_coverage

## 4. Трек B: Ценовой движок (недели 3-10)

### B1. Кластеризация позиций меню (недели 3-4) — ✅ ВЫПОЛНЕНО (2026-05-26)

**Цель:** классифицировать каждый SKU по роли в меню. ТЗ определяет 5 ролей — от этого зависит стратегия ценообразования и ограничения оптимизатора.

**Роли из ТЗ (п.4.7):**

| Роль | Код | Кол-во SKU | Доля | Стратегия по цене |
|---|---|---|---|---|
| **Премиум-якорь** | `premium_anchor` | 5,248 | 47% | Цена только вверх, осторожно |
| **Драйвер маржи** | `margin_driver` | 3,131 | 28% | Поиск оптимума: умеренные повышения |
| **Драйвер трафика** | `traffic_driver` | 1,592 | 14% | Цена стабильная, защищает поток гостей |
| **Хвост** | `tail` | 876 | 8% | Кандидаты на снятие/переработку |
| **Имиджевые / редкие** | `image_rare` | 218 | 2% | Цена премиальная, не оптимизируется по объёму |

**Метрики кластеризации:** Silhouette score = **0.3652** (хорошее разделение).

**Подход — реализован:**

Шаг 1 — 5 признаков из `sku_weekly_summary` (90-дневное окно, ≥3 недель продаж):
- `qty_share` — доля объёма продаж в подразделении
- `revenue_share` — доля выручки в подразделении
- `gp_margin` — средняя GP маржа
- `demand_cv` — коэффициент вариации спроса (стабильность)
- `price_index` — средняя цена / медиана категории

Шаг 2 — KMeans(k=5):
- Log-transform для right-skewed фич (qty_share, revenue_share, price_index)
- StandardScaler нормализация
- KMeans(k=5, n_init=20, random_state=42) — глобальная кластеризация (все 11k SKU×dept)
- Маппинг кластеров → роли через scoring-heuristic по центроидам
- Greedy assignment по бизнес-приоритету: traffic_driver → margin_driver → premium_anchor → tail → image_rare

**Результат:**

Таблица `sku_menu_role` (миграция `020_sku_menu_role.sql`):
```
sku_menu_role (
  id BIGSERIAL PK,
  product_id BIGINT FK→product,
  department_id UUID FK→departments,
  auto_role TEXT NOT NULL,           -- ML-кластер
  manual_role TEXT,                  -- ручное переопределение управляющим
  effective_role TEXT GENERATED ALWAYS AS (COALESCE(manual_role, auto_role)) STORED,
  features JSONB,                    -- 5 признаков для прозрачности
  cluster_meta JSONB,               -- cluster_id, silhouette, centroid_dist, run_date
  updated_at TIMESTAMP NOT NULL,
  UNIQUE (product_id, department_id),
  CHECK auto_role/manual_role IN (5 валидных ролей)
)
```

**Ручное переопределение:** `PUT /api/pricing-analytics/menu-roles/{product_id}/{department_id}?manual_role=...` — manual_role побеждает auto_role через GENERATED column. Рекластеризация НЕ сбрасывает manual override.

**Реализация:**
- Сервис: `app/services/menu_clustering_service.py` (MenuClusteringService — KMeans + scoring + batch upsert)
- Scheduler: `app/services/scheduled_pricing_analytics.py` → Sunday 03:15
- API: 4 endpoints (GET menu-roles, GET menu-roles/summary, PUT menu-roles override, POST menu-roles/cluster)

**Ожидание бизнес-валидации:**
- [ ] Распределение ролей проверено с управляющими (≥1 сессия обратной связи)
- [ ] UI: бейдж роли на странице номенклатуры + возможность ручного переопределения

### B2. Оценка ценовой эластичности (недели 4-8) — ✅ ВЫПОЛНЕНО (2026-05-28), затем УЛУЧШЕНО на чистых ценах

**Реализация:** `app/services/elasticity_estimation_service.py`, миграция `021_sku_elasticity.sql`, модель `SkuElasticity`. OLS через numpy (`np.linalg.lstsq` + ручной расчёт SE), CI через `scipy.stats.t`. statsmodels в requirements (пока не используется — numpy OLS достаточно). Регрессия: log_price + month dummies + linear trend + category-level log_qty (DiD-контроль). Empirical Bayes shrinkage для SKU-уровня.

**⚠ КРИТИЧНОЕ УЛУЧШЕНИЕ (2026-05-28): переход на чистые каталожные цены.**

Первая версия использовала цену `выручка/количество` из `sku_weekly_summary`. Расследование показало, что эта цена **загрязнена миксом** (модификаторы, весовые позиции): ~49% высокооборотных SKU имели дневную волатильность цены >5% без реальных изменений в меню → measurement error → attenuation bias.

Решение: загружены настоящие каталожные цены через `GET /resto/api/v2/price` (Фаза 4, таблица `sku_catalog_price`, 163,433 интервала). Эластичность пересчитана на них: `DATASET_SQL` берёт цену из каталога, валидную на неделю; `GRADE_SQL` считает число **реальных** изменений цены приказами.

**Сравнение грязная → чистая цена (SKU-уровень):**
| Метрика | Грязная (выручка/qty) | Чистая (каталог) |
|---------|----------------------|------------------|
| avg ε | -0.379 | -0.419 |
| median ε | -0.414 | -0.472 |
| R² | 0.655 (ложно высокий) | 0.570 (честный) |

**Вывод расследования:** attenuation bias был, но **небольшой**. Неэластичность **реальна** — подтверждена на чистых данных. Даже на каталожных ценах median ε=-0.47; только 3% позиций эластичны (<-1, в основном дешёвый фастфуд: Самса -1.3), 56% умеренные, 41% неэластичны.

**Фактические результаты (lookback 730 дней, чистые цены):**
- 34,021 SKU×dept оценено
- По уровням: sku 2,927 (Grade A/B/C) / group 29,612 / global 1,482
- По грейдам (по числу реальных цен): A 137, B 478, C 6,422, D 26,984
- Global prior ε = -0.106 (пул по всему, слабый fallback); group/sku сходятся на -0.42

**⚠ Бизнес-инсайт (подтверждён):** премиум-спрос в массе неэластичен (|ε|<1) → оптимизатор корректно рекомендует поднимать цены. Меню недооценено. Защита — human-in-the-loop + min_frequency. Эластичные позиции (фастфуд) система НЕ повышает вслепую.

**Достоверность для продакшена:** SKU-уровень (2,927 пар, R²=0.57) — надёжен для реальных изменений цен. Group-уровень (29,612, R²=0.17) — направленно верен, но индивидуальные числа шумны → для них применять консервативно.

**Цель:** для каждого SKU оценить, как изменение цены влияет на спрос. Это ключевой вход для оптимизатора.

**Проблема (явно обозначена в ТЗ):** в премиальном сегменте цены меняются редко — 2-3 раза в год. За 24 месяца на одну позицию мы получим 3-6 ценовых событий. Этого категорически мало для позиционной эластичности.

**Подход — иерархическая байесовская модель (как требует ТЗ п.4.3):**

Иерархия shrinkage:
```
Уровень 0: Глобальный prior (все позиции всех ресторанов)
  └─ Уровень 1: Категория блюд (супы, горячее, десерты, напитки...)
      └─ Уровень 2: Роль в меню (из B1: якорь / драйвер маржи / ...)
          └─ Уровень 3: Конкретный SKU × подразделение
```

Логика: SKU с малым числом наблюдений «заимствует» оценку у своей категории/роли. SKU с достаточным числом наблюдений получает собственную оценку. Модель автоматически решает, на каком уровне «остановиться» — это свойство байесовской иерархии.

**Реализация в два этапа:**

Этап 2a (неделя 4-5) — быстрая baseline-модель:
- Category-level log-log regression: `log(Q) = α + β × log(P) + controls`
- Controls: day_of_week, month, trend
- Даёт грубую оценку эластичности по категориям (не по SKU)
- Быстро реализуется, даёт первые цифры для дашборда

Этап 2b (неделя 5-8) — полная иерархическая модель:
- PyMC или NumPyro
- Вход: `sku_price_history` (ценовые события) + `sku_daily_sales` (объёмы до/после)
- DiD-подход (Difference-in-Differences): для каждого ценового события сравниваем изменение qty данного SKU vs контрольная группа (аналогичные SKU без изменения цены в тот же период)
- MCMC sampling → posterior distribution → point estimate + credible interval

**Выход:**

Новая таблица:
```
sku_elasticity (
  product_id BIGINT NOT NULL,
  department_id UUID NOT NULL,
  elasticity_mean NUMERIC(8,4),        -- точечная оценка (обычно отрицательная)
  elasticity_ci_lower NUMERIC(8,4),    -- 95% credible interval
  elasticity_ci_upper NUMERIC(8,4),
  n_price_events INTEGER,              -- кол-во наблюдённых изменений цены
  estimation_level TEXT,               -- 'sku' / 'role' / 'category' / 'global'
  reliability_grade TEXT,              -- A / B / C / D
  model_version TEXT,
  updated_at TIMESTAMP NOT NULL,
  UNIQUE (product_id, department_id)
)
```

Шкала надёжности:
- **A**: ≥ 10 ценовых событий, узкий CI (|CI| < 0.5), оценка на уровне SKU
- **B**: 5-9 событий, средний CI, оценка на уровне SKU или роли
- **C**: 2-4 события, широкий CI, оценка заимствована из категории
- **D**: 0-1 событие, оценка = global prior (наименее надёжная)

**Контролируемые эксперименты (ТЗ п.4.3 — A/B):**

Для позиций с grade D рекомендовать управляющим провести контролируемое изменение цены:
- Изменить цену на ±3-5% на 2 недели
- Сравнить qty с предыдущими 2 неделями и с контрольными позициями
- Результат → обновление эластичности

Механизм: пометка в UI «рекомендован эксперимент» + инструкция для управляющего. Не автоматическое изменение — human-in-the-loop.

**Definition of done:**
- Эластичность оценена для ≥ 80% активных SKU (top-200 по выручке — все).
- Для ≥ 30% SKU grade A или B.
- Результаты проверены бизнес-аналитиком на здравый смысл (например, базовые блюда более эластичны, чем десерты; алкоголь менее эластичен).

### B3. Ценовой оптимизатор (недели 7-9)

**Цель:** для каждого SKU рассчитать оптимальную цену, максимизирующую GP с учётом всех ограничений.

**Математическая формулировка (из ТЗ п.4.6):**

```
max  Σᵢ (Pᵢ − COGSᵢ) × Qᵢ(Pᵢ)

s.t.
  Pᵢ ∈ [Pᵢ_min, Pᵢ_max]                        -- ценовой коридор
  |Pᵢ − Pᵢ_current| / Pᵢ_current ≤ Δ_max       -- макс. шаг (default ±5%)
  (Pᵢ − COGSᵢ) / Pᵢ ≥ margin_min                -- мин. маржа (default 60%)
  Pᵢ / Pᵢ_market ≥ k                             -- мин. конкурентный индекс (если есть)
  Pᵢ = round(Pᵢ, rounding_step)                  -- округление (50₸ / 100₸)
  role = 'premium_anchor' ⟹ Pᵢ ≥ Pᵢ_current     -- якоря только вверх
  role = 'traffic_driver' ⟹ |ΔPᵢ| ≤ Δ_traffic   -- трафик-драйверы осторожнее
```

Где `Qᵢ(Pᵢ)` — прогноз спроса:
```
Qᵢ(Pᵢ) = Qᵢ_base × (Pᵢ / Pᵢ_current) ^ εᵢ
```
- `Qᵢ_base` — текущий прогноз спроса из SKU LightGBM модели
- `εᵢ` — эластичность из B2 (отрицательное число)

**Технически:**

Для ~200-500 активных SKU в одном ресторане — задача небольшая. Решается:
- `scipy.optimize.minimize` (SLSQP) — если гладкая формулировка
- `Optuna` — если нужна дискретная оптимизация (округление как hard constraint)
- Для первой версии: перебор по сетке (grid search) с шагом 50₸ в пределах коридора ±5% — пространство поиска маленькое (~5-10 вариантов на позицию), зато гарантированно находит оптимум и легко объяснить

**Каннибализация (кросс-эластичность):**

В первой версии — **не реализуем**. Причины:
- Кросс-эластичность требует значительно больше данных (одновременные изменения цен пар позиций).
- Для 500 SKU матрица 500×500 — нереалистично оценить.
- Во второй итерации: определить top-20 пар субститутов экспертно (шеф-повар знает, что Цезарь с курицей каннибализирует Цезарь с креветками) и добавить cross-price terms только для них.

**Результат:**

Новая таблица:

- Ответы с цитированием конкретных метрик через function calling
- Это самая сложная часть LLM-трека, делать после пилота

### C5. Ролевая модель по ТЗ (недели 9-10) — ✅ ВЫПОЛНЕНО (2026-06-11)

## 6. Трек D: Конкурентный анализ (недели 6-10)

**Приоритет: средний.** ТЗ явно указывает: «конкурентный индекс — это ограничение, а не цель». Для премиального сегмента собственное позиционирование важнее реакции на конкурентов. Этот трек не блокирует MVP оптимизатора.

### D1. Ручная загрузка цен конкурентов (недели 6-7)

**Минимальное решение:** управляющий вручную вводит цены из меню конкурентов.

**Таблицы:**
```
competitor (
  id BIGSERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  type TEXT,                     -- restaurant / delivery / cafe
  city TEXT,
  url TEXT,
  is_active BOOLEAN DEFAULT true,
  created_by UUID,
  created_at TIMESTAMP DEFAULT NOW()
)

competitor_price (
  id BIGSERIAL PRIMARY KEY,
  competitor_id BIGINT REFERENCES competitor(id),
  product_mapping_id BIGINT,     -- NULL если мэппинг не создан
  item_name TEXT NOT NULL,       -- название у конкурента
  price NUMERIC(14,2) NOT NULL,
  observed_at DATE NOT NULL,
  source TEXT DEFAULT 'manual',  -- manual / parser
  UNIQUE (competitor_id, item_name, observed_at)
)

product_competitor_mapping (
  id BIGSERIAL PRIMARY KEY,
  product_id BIGINT REFERENCES product(id),
  competitor_id BIGINT REFERENCES competitor(id),
  competitor_item_name TEXT NOT NULL,
  similarity_score NUMERIC(4,3),  -- от эмбеддингов
  is_confirmed BOOLEAN DEFAULT false,
  confirmed_by UUID,
  UNIQUE (product_id, competitor_id)
)
```

**UI:** простая форма — выбрать конкурента → ввести позицию + цену. Или импорт из Excel.

### D2. Парсер агрегаторов (недели 8-9)

**Источники (по приоритету):**
1. Wolt — структурированное API (если доступно)
2. Glovo — аналогично
3. Yandex Eda — аналогично
4. Сайты конкурентов — scraping (наименее надёжный)

**Архитектурное решение:** парсер — **отдельный микросервис** (не в основном приложении). Парсеры ломаются при обновлениях сайтов, не должны ронять систему ценообразования. Запись результатов в `competitor_price` через API.

**Частота:** 1 раз/неделю (cron), с возможностью внепланового запуска.

### D3. Мэппинг позиций (недели 9-10)

**Подход:**
- `sentence-transformers` (multilingual) для эмбеддингов названий позиций
- Косинусная близость → top-3 кандидата для каждой нашей позиции
- UI: таблица «наша позиция → кандидат конкурента → score → [Подтвердить] [Отклонить]»
- Подтверждённые мэппинги → `product_competitor_mapping.is_confirmed = true`

**Price Index:**
- Для каждой позиции: `our_price / median(competitor_prices)`
- Агрегат по ресторану: средний Price Index
- Ограничение в оптимизаторе (B3): `Price Index ≥ k` (default k=1.0 — не ниже медианы)

## 7. Пилот (недели 11-14)

### 7.1 Условия запуска пилота

- [ ] Backfill чеков ≥ 18 месяцев
- [ ] SKU-модель обучена, MAPE ≤ 25% по top-100
- [ ] Эластичность оценена для ≥ 80% активных SKU
- [ ] Оптимизатор генерирует рекомендации
- [ ] UI рекомендаций работает (approve/reject)
- [ ] LLM-обоснования генерируются
- [ ] Все бизнес-правила реализованы и настроены
- [ ] Управляющий обучен работе с системой (≥1 сессия)

### 7.2 Scope пилота

- **Один ресторан** (рекомендация: один из ресторанов «Сандык» с наибольшим объёмом данных).
- **Ограниченный набор позиций:** top-50 по выручке + 10-15 позиций из каждого кластера.
- **Длительность:** 4 недели (2 цикла по 2 недели, учитывая ограничение «не чаще 1 раза в 2 недели»).

### 7.3 Метрики пилота (из ТЗ п.14)

| Метрика | Порог приёмки |
|---|---|
| ΔGP (валовая прибыль) vs baseline | Статистически значимый прирост (CI не пересекает 0) |
| MAPE прогноза спроса (top-100 SKU, 7 дней) | ≤ 25% |
| WAPE по ресторану | ≤ 20% |
| Доля адекватных LLM-объяснений | ≥ 85% (выборочная проверка) |
| Время от рекомендации до отображения | ≤ 10 минут |
| Доля принятых рекомендаций | ≥ 60% |

### 7.4 Фидбек-loop

После каждого 2-недельного цикла:
1. Сравнить фактический GP с ожидаемым (из `price_recommendation.expected_gp`)
2. Обновить эластичности на основе наблюдённой реакции спроса
3. Скорректировать параметры оптимизатора
4. Собрать обратную связь от управляющего

## 8. Что не входит в MVP (делать после пилота)

| Компонент | Причина отложить | Когда делать |
|---|---|---|
| Каннибализация (кросс-эластичность) | Недостаточно данных для cross-price матрицы | После 6+ мес. ценовых экспериментов |
| Ad-hoc чат с LLM | Сложный RAG, не блокирует ценность | После пилота |
| N-BEATS / TFT (нейросетевые модели) | LightGBM достаточен для масштаба | Только если MAPE не достигнет порога |
| MLflow / Feature Store | Оверинжиниринг для 2 брендов | При масштабировании на 3+ бренда |
| Kubernetes | Docker Compose справляется | При горизонтальном масштабировании |
| Airflow/Dagster | APScheduler покрывает задачи | При 20+ пайплайнах |
| Автоматическая выгрузка цен в iiko | ТЗ Phase 1: «выгрузка для ручной загрузки» | После подтверждения эффекта пилотом |
| Grafana / Prometheus | Базовый мониторинг через health checks | При переходе к SLA 99% |
| Экспорт PDF/PPTX | Excel достаточен для Phase 1 | По запросу бизнеса |
| SSO / MFA | Phone-based login достаточен | При требовании security audit |
