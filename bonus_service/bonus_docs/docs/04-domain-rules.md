# 04. Бизнес-правила

Все правила, которые должны быть зашиты в логику расчёта.

## 1. Период расчёта

- **Календарный месяц** (с 1-го по последнее число)
- Расчёт делается **после закрытия месяца**, обычно 1-5 числа следующего
- При расчёте используется **схема, активная на последний день периода**
  ```python
  scheme_lookup_date = period_end  # 2026-04-30 для апреля
  ```
- Один сотрудник = одна запись расчёта на месяц (UNIQUE на `employee_id + period_year + period_month + status='approved'`)

## 2. Учёт смен (shifts proration)

**Правило:** если в config модели стоит `apply_shifts_proration: true`, бонус пропорционален отработанным сменам.

```python
proration_ratio = shifts_worked / shifts_norm
bonus = base_bonus * proration_ratio
```

**Источник смен:** TCO (Time Control Office)

**Что такое норма смен:**
- Берётся из `monthly_plan` или захардкожено по специфике должности (уточнить у заказчика)
- Для MVP: **22 смены** для всех — потом подкрутим

**Если сотрудник работал 0 смен:** бонус = 0, расчёт не сохраняется (или сохраняется со статусом `skipped`).

**Дробные смены:** допустимы (если TCO считает по часам).

## 3. Испытательный срок

**Правило (по документу):**
> Доплата может быть не выплачена по решению директора... для всех сотрудников, проходящих испытательный срок.

**В системе:**
- Поле `employee_assignment.employment_type = 'probation'` + `probation_until = '2026-04-30'`
- При расчёте проверяем: попадает ли период расчёта в `probation_until`?
- Если попадает → флаг `is_probation_period: true` в результате
- По умолчанию **бонус не выплачивается** (`final_bonus = 0`), но можно переопределить вручную (поле `override_probation_payment`)

## 4. Стажировка бариста

**Правило (по документу):**
> Подсчёт бонусов и их начисление официантам производится исключительно после 3-х (трёх) дней стажировки.

**Применять к:** Бариста и Официант (по контексту документа похоже на оба, уточнить)

**В системе:**
- Если у сотрудника `hired_at` попадает в текущий период (новый сотрудник в этом месяце)
- И прошло меньше 3 дней с `hired_at` до конца периода — бонус 0
- Если прошло >= 3 дней, считать только за дни **после стажировки**

## 5. KPI Scoring

```python
def score_kpi(fact: Decimal, target: Decimal, direction: str, cap_at_100: bool = True) -> Decimal:
    """Возвращает % выполнения KPI."""
    
    if fact is None or target is None or target == 0:
        return Decimal(0)
    
    if direction == "higher_is_better":
        # план продаж: 102/100 = 102%
        result = (fact / target) * 100
    
    elif direction == "lower_is_better":
        # негативные отзывы: цель 5%, факт 3% → перевыполнили
        # (target / fact) даёт >100% если fact < target
        if fact == 0:
            result = Decimal(100)
        else:
            result = (target / fact) * 100
    
    elif direction == "binary":
        # рейтинг ресторана: 5 → 100%, 4 → 80%, 3 → 60%
        result = (fact / target) * 100
    
    if cap_at_100:
        result = min(result, Decimal(100))
    
    return result.quantize(Decimal("0.01"))


def overall_kpi(kpi_results: list[Decimal]) -> Decimal:
    """Среднее арифметическое (без весов в текущей версии)."""
    if not kpi_results:
        return Decimal(0)
    return (sum(kpi_results) / len(kpi_results)).quantize(Decimal("0.01"))
```

**Веса KPI:** в текущих документах все KPI равны (просто среднее). Архитектурно поле `weight` в `scheme_kpi` зарезервировать на будущее — по умолчанию 1.

## 6. Грейды (поиск коэффициента)

```python
def find_grade(grades: list[Grade], percent: Decimal) -> Grade | None:
    """Вернуть грейд, в который попадает percent. None если ниже минимума."""
    for grade in sorted(grades, key=lambda g: g.from_percent):
        if grade.from_percent <= percent <= grade.to_percent:
            return grade
    return None  # ниже минимального порога → бонус 0
```

**Пример таблицы:**
```
70-79%  → 80 000 тг
80-84%  → 100 000 тг
85-89%  → 130 000 тг
90-97%  → 150 000 тг
98-100% → 170 000 тг
```

**Краевые случаи:**
- 87% → грейд 85-89% → 130 000 тг ✓
- 89.5% → попадает в 85-89%? **Решение:** поля `from_percent` и `to_percent` хранятся как DECIMAL, граница включительная сверху по предыдущему. То есть 85-89.99 эквивалентно 85-89, а 90-97 = 90.00-97.99. **Но в документах границы как 70-79, 80-84, 85-89, 90-97, 98-100** — между ними дырки! Это значит, что 89.5% или 79.5% попадает в верхний грейд (89.5 → 90-97). Уточнить у бизнеса. Для MVP: **округление в большую сторону до целого**, то есть 89.5% → 90% → грейд 90-97%.

Зафиксированное правило MVP:
```python
percent_int = math.ceil(percent)  # 89.5 → 90
# дальше ищем грейд по percent_int
```

## 7. Удержания и штрафы

**По документу:** до 100% от бонуса.

**Источник:** служебная записка от руководителя (вне системы), вводится вручную.

**В системе:**
- Запись в `calculation_penalty` со ссылкой на документ
- Поддерживаем как процент (0-100), так и абсолютную сумму
- Применяются **после** базового расчёта:
  ```python
  final_bonus = base_bonus - sum(penalties_amount)
  if final_bonus < 0:
      final_bonus = 0
  ```

## 8. Округление

- Все вычисления в `Decimal`, контекст `ROUND_HALF_UP`
- **Промежуточные** значения округляются до 2 знаков (тиыны/копейки)
- **Финальный** бонус — целое число тенге (ROUND_HALF_UP до 0 знаков)
  ```python
  final_bonus = base_bonus.quantize(Decimal("1"), rounding=ROUND_HALF_UP)
  ```

Пример: `2 500 000 × 0,045 = 112 500.00` — целое уже.  
Пример: `2 000 000 × 0,1% = 2 000.00` — целое.  
Пример: `25 000 000 / 22 × 20 × 0,33% = 75 000.00` — округляем до 75 000.

## 9. Даты схемы и перерасчёт

- При сохранении новой версии схемы старая закрывается на `new.effective_from - 1 день`
- Расчёты со статусом `paid` не пересчитываются (только новый расчёт)
- Расчёты со статусом `draft`/`review` — можно пересчитать с новой схемой (с пометкой `recalculated_from = old_id`)

## 10. Валидация config схемы

При создании/обновлении `bonus_scheme.config` валидируется через Pydantic-схему соответствующей модели:

```python
class SchemeConfigValidator:
    @staticmethod
    def validate(model_code: str, config: dict) -> None:
        validators = {
            "flat_by_kpi": FlatByKpiConfig,
            "revenue_percent_by_kpi": RevenuePercentByKpiConfig,
            ...
        }
        validators[model_code].model_validate(config)
```

**Что проверяется:**
- Все required поля на месте
- Все KPI-источники существуют в `DataSourceRegistry`
- Все revenue-источники существуют
- Грейды не пересекаются и не имеют дырок (для production — для MVP допускаем дырки)
- Сумма distribution_weights в команде не превышает 1.0 (валидация на уровне team, не scheme)

## 11. Налоги (NET vs GROSS)

**По документу:**
> Все расчёты, проценты, суммы доплат, указанные в Положении и Приложениях, приведены к выплате (net), т.е. после обязательных удержаний (подоходного налога, обязательных пенсионных взносов).

**Значит:**
- Все суммы в системе — это **NET** (на руки сотруднику)
- Бухгалтерия при выгрузке в 1С:ЗУП должна **накрутить gross** (умножить на коэффициент с учётом ИПН 10% + ОПВ 10%)
- Сервис gross не считает — это работа 1С

## 12. Идемпотентность расчёта

Запуск расчёта за один период несколько раз должен:
- Создавать новый `bonus_calculation` со статусом `draft`
- Старый `draft` за тот же период удалять (или помечать `superseded`)
- Если есть `approved`/`paid` — не трогать, новый помечать `recalculated`

## 13. Что делать если данных нет?

| Ситуация | Поведение |
|---|---|
| Нет схемы для (location, position) | Ошибка, не считаем |
| KPI значение отсутствует (например, аудит не проведён) | Считаем как 0%, влияет на средний |
| Выручка из iiko = 0 | Бонус = 0 |
| Нет данных о сменах | Считаем как 0 смен (= бонус 0 если proration on) |
| Сотрудник уволен в середине месяца | Считаем за фактически отработанные смены |

## 14. Логирование

Каждый расчёт логирует:
- Все вызовы источников данных (с параметрами и результатом)
- Промежуточные значения (KPI fact/target/percent, выручка, смены)
- Применённый грейд и коэффициент
- Применённые штрафы
- Финальный bonus

Это всё дублируется в `bonus_calculation.breakdown` (JSONB), чтобы потом не лезть в логи.
