## 1. Executive Summary

### Реальное состояние моделей

| | Заявлено (CLAUDE.md) | Фактически (метаданные .pkl + прод-мониторинг + контрольный замер) |
|---|---|---|
| Department-модель | Test MAPE 6.18%, R² 0.9962 | **Прод-файл = отклонённая модель от 2026-07-05: test MAPE 48.8%**, val MAPE 28.4%. Честный WAPE ≈ 18–19%, R² ≈ 0.92. Прод-мониторинг (4 точки): дневной MAPE 10–37% |
| SKU-модель | «Phase 5.3, log1p, 600 деревьев» | **Заморожена с 2026-05-25**: test MAPE 60.6%, **test R² 0.10** (val R² 0.47 → сильная временная деградация). Еженедельный retrain падает по OOM |
| Per-segment модели | «не обучены, fallback на глобальную» | Верно; сегментация **эмпирически проверена и отклонена** 2026-04-30 (хуже на 2.3 п.п.) — см. §9 |

Цифра «6.18%» — артефакт эпохи до фикса утечки: `training_service.py:441-443` прямо документирует «~6% in-sample MAPE while collapsing to ~50% out-of-sample», а `docs/FORECAST_IMPROVEMENT_PLAN.md:11` признаёт реальный MAPE ≈ 50%. При этом 6.18% до сих пор растиражирован в `CLAUDE.md:620`, `docs/PRICING_SYSTEM_ROADMAP.md:47`, `docs/LABOR_OPTIMIZATION_ARCHITECTURE.md:60`.

### 3 главных риска (все подтверждены доказательствами из прода)

1. **Прод сейчас работает на отклонённой модели.** Контур переобучения записывает кандидата в `models/lgbm_model.pkl` **до** решения о деплое. 2026-07-05 кандидат с test MAPE 48.8% был «отклонён» (rejected), но остался в прод-файле, и после рестарта приложения в 03:48 именно он был загружен в память. Guardrail существует, но ничего не защищает (§4.1).
2. **SKU-retrain убивает весь API каждое воскресенье 03:45.** Zero-expansion строит сетку 11 501 пар × 181 день ≈ 2.1 млн строк × ~100 колонок; ядро OOM-kill'ит uvicorn (RSS 3.3 GB при 3.8 GB на хосте). Побочно: SKU-модель не обновлялась 6 недель, а рестарт после OOM — тот самый момент, когда в память попадает отклонённая dept-модель из риска №1 (§4.2).
3. **Тихая деградация SKU-инференса.** Признаки на инференсе вычисляются принципиально иначе, чем при обучении (rolling без zero-fill дней, константы вместо encodings, сломанный `same_weekday_avg`, `sku_rank_in_dept=50`). Модель с test R² 0.10 кормит `labor-demand` API для TCO (не pricing — см. §8) (§4.4).

### 3 самых выгодных улучшения

1. **Починить контур деплоя** (атомарная запись кандидата во временный путь, сравнение сопоставимых метрик, hot-reload синглтона) — S/M по сложности, устраняет риск №1 и делает все дальнейшие улучшения вообще осмысленными.
2. **Вынести/облегчить SKU-retrain** (downcast типов + обучение вне API-процесса или лимит памяти + swap-план) — M, устраняет еженедельный сбой API и размораживает SKU-модель.
3. **Переключить headline-метрику на WAPE/MedianAPE со стратификацией по масштабу и горизонту + ежедневный полный batch-прогноз в `forecasts` для всех 41 активных точек** — без честного измерения (сейчас мониторится 4 точки из 41, алерты никуда не отправляются) любые улучшения модели неверифицируемы.

## 4. Критичные проблемы (P0)

### P0-1. Кандидат перезаписывает прод-модель ДО решения о деплое; сейчас в проде — отклонённая модель ⬅ НОВОЕ

**Файлы:** `app/services/model_retraining_service.py:97-116`, `app/agents/sales_forecaster_agent.py:89` и `:224-225`, `:911-925`.

**Механика.** `auto_retrain_model` создаёт агента с дефолтным путём `models/lgbm_model.pkl` и вызывает `train_model` с дефолтным `save_model=True`:

```python
# model_retraining_service.py:97-98
new_forecaster = SalesForecasterAgent()          # model_path = "models/lgbm_model.pkl"
model, metrics = new_forecaster.train_model(train_df, val_df, test_df)  # save_model=True по умолчанию
```

`train_model` внутри (`sales_forecaster_agent.py:224-225`) вызывает `self._save_model(metrics)`, который пишет прямо в `models/lgbm_model.pkl` (`:924`). Затем сервис ещё раз явно сохраняет (`model_retraining_service.py:105`) и копирует прод-файл во «временный» (`:112`). Решение о деплое (`:149-151`) принимается **после** того, как прод-файл уже перезаписан. При `rejected` (`:181-183`) в архив уезжает temp-копия, а кандидат остаётся в `models/lgbm_model.pkl`.

**Доказательство из прода.** Лог 2026-07-05 03:00: `"Model v2.1 saved to models/lgbm_model.pkl"` (дважды) → `"⚠️ New model rejected. Reason: Performance degradation: 153.8% worse"`. Метаданные прод-файла: `trained_at: 2026-07-05T03:00:05`, `test_mape: 48.81` — это и есть отклонённый `v_20260705_030005_363d576e` (его же копия лежит в `models/archive/rejected_v_20260705_030005_363d576e.pkl`). В 03:48 приложение перезапустилось (см. P0-2) и загрузило с диска именно его. `forecast_accuracy_log`: дневной MAPE вырос с 10–16% (1–3 июля) до 23.9% (4 июля) и **37.1%** (5 июля).

**Смежный дефект — синглтон не перезагружается.** `get_forecaster_agent()` (`sales_forecaster_agent.py:1002-1007`) создаётся один раз; `reset_forecaster_agent()` не вызывается нигде (grep по коду пуст). Даже при честном деплое обслуживающий процесс работает на старой модели до следующего рестарта, а при рестарте загружает «что лежит на диске» — т.е. фактический выбор модели в проде случаен относительно deployment decision.

**Как проверить:** команды в §3; плюс `ls -la models/` — `lgbm_model.pkl` датирован временем retrain даже в недели с `rejected_v_*` в архиве.

**Как исправить:**
1. В `auto_retrain_model` создавать агента с временным путём: `SalesForecasterAgent(model_path=str(temp_model_path))` — тогда `_save_model` пишет в temp, а прод-файл трогает только `_deploy_model`.
2. В `_deploy_model` заменить `shutil.copy2` на «записать во временный файл + `os.replace()`» (атомарность на POSIX; сейчас `copy2` в `:371` может дать частично записанный файл параллельному читателю).
3. После деплоя вызывать `reset_forecaster_agent()` (или `agent._load_model()` под локом), чтобы serving-процесс подхватил новую модель без рестарта.

### P0-2. SKU-retrain каждое воскресенье 03:45 убивает весь API по OOM; SKU-модель заморожена с 25 мая ⬅ НОВОЕ

**Файлы:** `app/services/sku_model_retraining_service.py:21-51`, `app/services/sku_training_service.py:164-219`, `app/main.py:96-105`.

**Механика.** Retrain выполняется в том же процессе FastAPI (BackgroundScheduler, `main.py:96-105`). `_expand_zero_days` строит декартову сетку `active_pairs.merge(date_df, how='cross')` (`sku_training_service.py:173`): на текущих данных это 11 501 активных пар × 181 день ≈ **2.08 млн строк**, к которым мерджатся ~25 метаданных-колонок и затем добавляются ~40 фичей — несколько ГБ RAM на хосте с 3.8 GB.

**Доказательство из прода.** `/var/log/syslog`: `2026-07-05T05:48:01+02:00 ... Out of memory: Killed process 3822214 (uvicorn) total-vm:6582992kB, anon-rss:3304336kB` — ровно через 3 минуты после лога `03:45:00 UTC "Scheduler triggered: SKU model auto-retrain"`. RestartCount контейнера = 1, StartedAt = 2026-07-05T03:48:02Z. Косвенные подтверждения хронической природы: `sku_lgbm_model.pkl` от 2026-05-25 (6 недель без обновления при еженедельном расписании), каталог `models/sku_archive/` не существует (строка `_archive_model` ни разу не достигнута), рост меню с 634 тыс. строк датасета в мае (из .pkl: 444k+95k+95k) до ~2.1M сейчас объясняет, почему раньше проходило, а теперь падает.

**Каскадный эффект:** рестарт после OOM — это тот момент, когда в память загружается перезаписанная в 03:00 модель из P0-1. Две проблемы вместе образуют «каждое воскресенье прод пересаживается на свежего кандидата вне зависимости от решения guardrail».

**Как проверить:** `grep "Killed process" /var/log/syslog | grep uvicorn`; `docker inspect sales-forecast-app --format '{{.RestartCount}} {{.State.StartedAt}}'`; `ls models/sku_archive` (нет каталога).

**Как исправить (по возрастанию трудозатрат):**
1. Немедленно: снизить память датасета — `float32`/`int32` downcast, `category` dtype для метаданных, не тащить 25 raw-колонок через cross-join (мерджить метаданные после расчёта фичей), сократить `days` со 180 до 120.
2. Правильно: вынести обучение из API-процесса (отдельный контейнер/`docker exec` job или очередь) с memory-limit, чтобы OOM убивал job, а не API.
3. Добавить в `run_sku_auto_retrain` реальные guardrails (см. P0-5) — сейчас `MAX_MAPE_THRESHOLD=80` только пишет warning и всё равно сохраняет (`sku_model_retraining_service.py:32-38`).

### P0-3. Deployment decision сравнивает несопоставимые метрики → еженедельный лотерейный reject ⬅ НОВОЕ

**Файлы:** `app/services/model_retraining_service.py:238-263` и `:297-359`.

`current_mape` — скользящий 7-дневный MAPE прода из `forecast_accuracy_log` (`:243-250`): по 3–4 точкам из 41, после temporal smoothing, на реальных горизонтах. `new_mape` — offline test MAPE кандидата на 15% хвосте датасета (все 41 точка, включая мелкие с взрывным MAPE, без smoothing). 2026-07-05: 19.2% (прод) против 48.8% (offline) → «153.8% worse» → reject. Это сравнение яблок с паровозами: кандидат может быть строго лучше текущей модели и всё равно быть отклонён (и наоборот). Судя по архиву — 3 reject из 4 последних недель, т.е. прод-модель системно стареет (а из-за P0-1 фактически заменяется всё равно).

**Дополнительно:** `_get_current_model_performance` ищет ключ `'training_date'` в `model_info` (`:257`), которого не существует (агент кладёт `trained_at` внутрь metrics) → `version_id` всегда `'unknown'`, `model_age_days` всегда 0 (`:384-398`) → условие «retrain if older than 30 days» (`:278`) мертво.

**Как исправить:** сравнивать like-for-like — прогнать **обе** модели (текущий прод-pkl и кандидата) по одному и тому же hold-out окну (последние 14–28 дней, все точки, WAPE + MedianAPE), и деплоить по этому сравнению. Это S-размер: обе модели уже загружаемы, фичи строит один сервис.

### P0-4. Аудит-трейл переобучения мёртв: `np.float64` ломает INSERT ⬅ НОВОЕ

**Файлы:** `app/services/model_retraining_service.py:400-462`, `app/agents/sales_forecaster_agent.py:176-185`.

Метрики считаются как `np.float64` (например, `val_mape` из `_calculate_mape`), и psycopg2 не умеет их адаптировать. Лог 2026-07-05: `❌ Error saving model metadata: (psycopg2.errors.InvalidSchemaName) schema "np" does not exist ... np.float64(48.811...)` — обе записи (`model_versions`, `model_retraining_log`) откатываются. В таблицах — только 2 строки от 2025-06-30 (эпоха до numpy 2.x). Итог: UI/аналитика видят «переобучений не было год», решения reject/deploy нигде не фиксируются, кроме логов контейнера.

**Как исправить:** `float(...)` на все метрики перед записью (или общий `json.dumps(..., default=float)` / конвертер `register_adapter(np.floating, AsIs)`); плюс алерт на ошибку записи вместо тихого `db.rollback()`.

### P0-5. SKU-модель: train/inference-рассинхронизация фичей + утечка + непригодные метрики ⬅ НОВОЕ

Модель формально «обучена», но её инференс получает другие признаки, чем видел train, а сохранённые метрики не отражают пригодность. Из .pkl: val R² 0.47 → **test R² 0.10** (хронологический хвост) при MAPE 60.6% — модель едва лучше константы на новых периодах.

После этого честно перезамерить — не исключено, что модель нужно упростить (см. P2-6, intermittent demand).

## 5. Проблемы качества (P1)

### P1-1. `is_outlier_day` — оракульная фича (train видит таргет дня, инференс всегда 0)

`training_service.py:109-141`: флаг ставится, если `total_sales` **этого же дня** — IQR-выброс, причём квантили считаются по всему датасету (включая val/test-период — просачивание распределения через сплит). На инференсе флаг всегда 0 (`sales_forecaster_agent.py:534-539`, осознанное решение из плана, этап 3.5). Следствия: (а) test-метрики считаются с оракулом, которого у прода нет — замер в §3 даёт ~6.5 п.п. MAPE / 0.7 п.п. WAPE разницы; (б) модель обучена «выбросы объясняет флаг» → систематически недопредсказывает пики и провалы в проде. Важность фичи — 6-е место из 83 (130–190 сплитов). **Fix:** считать флаг только по train-окну ИЛИ честно: заменить на предсказуемые причины выбросов (банкеты — уже в плане 4.3, праздники, закрытия), а метрики всегда репортить с flag=0.

### P1-2. Auto-retrain использует `winsorize`, ручной `/retrain` — flag-only: две разные прод-политики

`model_retraining_service.py:83-88` явно передаёт `handle_outliers=True, outlier_method='winsorize'`, тогда как план (этап 3.5) объявил winsorize отключённым, и `/api/forecast/retrain` (`routers/forecast/core.py:55-65`) обучает без него. Модель из воскресного контура и модель из ручного эндпоинта — разные по обработке таргета, их метрики несравнимы (42.99% vs 50.69% MAPE в §3 — на треть «улучшение» просто от клиппинга test-таргета). **Fix:** один путь обучения, одна политика.

### P1-3. Три расходящихся календаря праздников; даты Курбан-айта заканчиваются 2026 годом

- `training_service.py:851-891` (train): Наурыз 21–23, Независимость 16–17, Курбан-айт словарём 2022–2026 (`:881-887`).
- `sales_forecaster_agent.py:621-636` (инференс dept): Наурыз 21–**24**, Независимость 16–**18**, **без Курбан-айта**.
- `forecast_postprocessing_service.py:465-484` (пост-обработка): третий вариант.

Т.е. фича `is_holiday` в проде вычисляется не так, как при обучении, — классическая тихая деградация. С 2027-01-01 Курбан-айт молча исчезает и из train. Нет: Рамадана (сдвигает выручку общепита на недели!), переносов выходных постановлениями правительства, зарплатных дней (1–5/10-е, 25-е), школьных каникул, 7 января. **Fix:** единый модуль/таблица календаря (пакет `python-holidays` для КЗ + ручные добавки) — уже в плане как 4.9, но важно именно **единство** train/inference.

### P1-4. Multi-day горизонт: lag-фичи со сдвинутой семантикой (известно из плана — 4.4, не сделано)

`forecast()` для `days_ahead>1` подаёт `lag_1d_sales` = последний доступный факт, а не «вчера от прогнозной даты» (`sales_forecaster_agent.py:281-293`); train таких строк не видел. Честный 30-дневный backtest в плане показал деградацию h=1 27% → h=22-30 36% MAPE и bias месячного агрегата −13.5%. Основная бизнес-задача — график смен на месяц — живёт именно на этих горизонтах. **Fix:** hybrid horizon-модели (план 4.4-B) или явная фича `days_ahead` + обучение на смещённых окнах.

### P1-5. Двойное сглаживание + произвольные множители в post-processing

Прогноз режется дважды: `_apply_temporal_smoothing` в агенте (±50% от среднего того же DOW за 4 недели, `sales_forecaster_agent.py:686-753`) и — для `/batch_with_postprocessing` — ещё раз ±50% от 7-дневного среднего (`forecast_postprocessing_service.py:214-256`). Второй клип игнорирует день недели: пятница/суббота у точки с выраженной недельностью легко выходит за +50% от недельного среднего → пики срезаются. Поверх этого — рудименты «weekend boost», удалённого из агента ещё в апреле: `×1.1` для кофеен в выходные и `×1.15` возле праздников (`forecast_postprocessing_service.py:297-308`) — ровно тот класс ручных множителей, который backtest в плане (§2.4 п.1) признал вредным. CI — нормальное приближение с CV-капом 0.5 (`:360-413`), не quantile/conformal; anomaly detection — z-score против 30-дневного среднего без учёта DOW (`:312-358`) → выходные системно «аномальнее». **Fix:** выпилить множители, оставить один clamp (лучше DOW-aware), CI — через квантильную LightGBM или split-conformal по остаткам последних недель.

### P1-6. Разные формулы std и окон train vs inference (dept-модель)

Train: `pandas.rolling(...).std()` (ddof=1) по `shift(1)`-ряду **строк с продажами** (`training_service.py:463-465`); inference: `np.std` (ddof=0) по окну из 30-дневной выборки (`sales_forecaster_agent.py:457-459`). Для коротких окон расхождение 15–20%. Также train `rolling_30d` = окно 30 строк, inference — среднее всех строк 31-дневного окна. Дни закрытий (`total_sales=0` отфильтрованы в `training_service.py:66`) сжимают лаги: `lag_7d` — «7 торговых дней назад», не календарная неделя, — согласованно между train и inference, но семантически шумно для сезонных точек с простоями. **Fix:** зафиксировать ddof и оконную семантику в общем feature-builder'е.

### P1-7. Метрика: MAPE по точкам смешанного масштаба; отчётные цифры несопоставимы между путями

MAPE взрывается на мелких точках (§3: WAPE 18% при MAPE 43–51%); разные пути обучения (winsorize/flag) дают несравнимые MAPE; deployment decision (P0-3) построен на этом же. План уже пришёл к MedianAPE как приоритету (§5 плана) — осталось довести до кода: в `train_model`, в deployment decision и в мониторинге репортить WAPE + MedianAPE + стратификацию (масштабные квартили, сегменты, горизонты). Бэктест на нескольких окнах: сейчас метрика — с одного 15% хвоста; rolling-origin backtest по 3–4 окнам дал бы доверительный интервал на сравнение моделей.

### P1-8. SKU: log1p/expm1 без коррекции смещения + округление

`np.expm1(mean(log-pred))` систематически занижает матожидание (Jensen); для dept-модели bias −11…−13.5% уже зафиксирован в плане (3.1, «отложено»). Для SKU при слабом сигнале эффект тонет в шуме R² 0.10, но после починки P0-5 стоит добавить smearing-поправку или квантильный objective. `predict().round(1)` (`sku_forecaster_agent.py:158`) — дробные qty приемлемы для планирования, вопрос закрыт осознанно.

## 10. Roadmap

Принцип: **сначала чинится измерение и контур деплоя, потом модель** — улучшать модель, чьи метрики не отражают прод и чей деплой случаен, бессмысленно.

**Фаза 0 — остановить кровотечение (дни):**
1. Восстановить прод dept-модель: задеплоить последний честно принятый бэкап (`backup_lgbm_model_20260621_030006.pkl`, test MAPE 44.4 — лучше текущих 48.8) или прогнать оба по hold-out и выбрать; рестарт.
2. P0-1: temp-path + `os.replace` + reload синглтона.
3. P0-4: `float()` в метрики → аудит-трейл оживает.
4. P0-2 (минимум): отключить/перенести SKU-retrain, пока не решена память — воскресный OOM хуже, чем stale SKU-модель.

**Фаза 1 — честное измерение (1–2 недели):**
5. WAPE + MedianAPE + стратификация в train/deploy/мониторинг; like-for-like deployment decision (P0-3).
6. Ежедневный полный batch-прогноз в `forecasts` (41 точка, t+1 и t+7), SKU — в `sku_forecasts`; алерты наружу (P0-6).
7. Rolling-origin backtest как штатная приёмка (расширить `backtest_30day.py`).

**Фаза 2 — SKU-модель (2–4 недели):**
8. Единый feature-builder, устранение пунктов a–h из P0-5; retrain вне API-процесса.
9. Tweedie/two-stage для intermittent; метрики с учётом нулей.
10. Только после этого — решать, годится ли SKU-прогноз для labor-demand (и обновить `data_quality`-флаги для TCO).

**Фаза 3 — точность dept-модели (по плану FORECAST_IMPROVEMENT_PLAN, приоритеты подтверждаю):**
11. Единый календарь (№7) → банкеты (№8) → hybrid horizon (№5) → квантильные прогнозы (№9) → погода (№10).
12. Гигиена: мёртвые фичи, мёртвый код, унификация winsorize/flag (P1-2).
